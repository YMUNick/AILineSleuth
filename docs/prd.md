## 2. 一句話定位

> 給東南亞和台灣中小代工廠夜班主管用的異常調查 Copilot：一按 Investigate，Gemini 用固定查詢函式在 BigQuery 找證據、推出根因、開出工單，把停線調查從 40 分鐘縮到 90 秒，而且每個結論都查得到證據。

差異化（對評審）：Siemens Industrial Copilot、Cognite、Google MDE 賣的是已經有 MES 的大廠；我們服務的是資料還在 Excel 和 PLC CSV 的中小代工廠，按產線月付，搭「中國+1」產能移往 JAPAC 的趨勢。

## 3. 目標使用者與情境

- **主要使用者：夜班產線主管**（中小代工廠，50–300 人規模，沒有 MES）。凌晨出事時通常只有他一個人負責判斷，工程師不在現場。
- **痛點**：停線以後要翻 Excel、PLC 匯出的 CSV、交班紀錄和 SOP，找原因平均要 40 分鐘（**待訪談驗證**）；停一小時損失 X 萬（**只能填受訪者的原話，沒問到就寫「待驗證」**）。
- **次要使用者：維修技術員**，在手機上收到工單（MVP 用掃 QR code 開啟，不做推播）。
- **採購決策者**：廠長或老闆（訪談時確認，見 `docs/sales/interview-guide.md`）。
- **MVP 情境**：03:00，Line 2 因為過溫停線，夜班主管打開 LineSleuth。

## 4. MVP 使用者流程（對應 Dana 五格分鏡，總長 90 秒）

| 格 | 時間點 | 使用者看到 / 做的事 | 對應功能 |
|---|---|---|---|
| ① | 0–10s | 03:00，2D 產線俯視圖上的 Line 2 機台亮紅燈，計時器開始跑 | F1 |
| ② | 10–15s | 主管按下唯一的 **Investigate** 按鈕（沒有聊天輸入框） | F2 |
| ③ | 15–60s | 時間軸上一張一張長出證據卡：查詢名稱、數值、時間、證據小圖；點開可以看 BigQuery 原始列 | F3、F4 |
| ④ | 60–75s | 結論卡：根因＋信心標籤＋建議處置；產線圖同時把 CV-2 閥門標成 `ROOT CAUSE` | F5、F1 |
| ⑤ | 75–90s | 大螢幕顯示 QR code，評審用手機掃描後開出英文工單；按 `Show summary` 開 Recap 收尾畫面（After＝這次實測秒數，Before 只在有真實基準時顯示；畫面上不寫死「40 min」） | F7、F10 |
| 加演 | 另 30s | 切到正常資料的情境再按 Investigate，出現灰卡「Insufficient evidence」 | F6、F8 |

## 5. 功能需求

| 編號 | 功能 | 說明 | 驗收條件 |
|---|---|---|---|
| **F1** | 產線狀態畫面與根因高亮 | SVG 俯視圖（`line-layout-v2.svg`），機台用顏色表示狀態（正常／警示／停線），異常機台亮紅燈並顯示停線計時器。調查中鏡頭拉近焦點機台；結論出現後把根因標在圖上：根因用琥珀、停線用紅（UI v2 §2） | 載入劇本後 Line 2 顯示紅色＋計時器；切到正常情境時全部是正常色。主線結論出現後：L2-M3 外框轉琥珀實線、CV-2 閥門琥珀高亮並出現 `ROOT CAUSE`，L2-M3 本體仍是紅色 `STOPPED`；灰卡時不標任何根因，Line 1 灰色虛線外框＋`No root cause found`；根因不在對照表內就不標位置（不替模型猜）；Reset／切換情境全部清除。動畫只限第 7 節「動態」列出的範圍，`prefers-reduced-motion: reduce` 時全部關閉 |
| **F2** | Investigate 觸發 | 每個畫面只有一個 Investigate 按鈕，把異常事件（產線、機台、時間）送進後端 | 按下後 1 秒內出現「調查中」狀態；調查進行中按鈕不能再按（避免重複觸發燒錢） |
| **F3** | Agent 調查 | Vertex AI Gemini function calling，只能從約 5 個固定查詢函式挑選並填入參數，temperature 0；SOP 直接放在 prompt 裡。函式的具體設計由 Eddie 決定，至少要能查到：異常時間窗內的感測器數值、警報/事件紀錄、交班與維修紀錄、和正常基準的比較 | Gemini 不會產生或執行任何自由 SQL；同一題連跑 3 次，選到的函式和結論都一樣；每次調查的函式呼叫和參數都會寫進 Cloud Logging |
| **F4** | 證據卡時間軸與小圖 | 每次函式呼叫就產生一張卡片：查詢名稱、關鍵數值、時間範圍、一張內嵌 SVG 證據小圖（依卡片種類四選一：事件時間軸／數值＋SOP 上限／數值 vs 基準／指令 vs 實際，UI v2 §1）；點開可以看對應的 BigQuery 原始列。舊卡收合成精簡列（附迷你圖） | 卡片和小圖上的每個數字都能在原始列裡找到一樣的值（Quinn 抽查）；小圖不平滑、不插值、缺值就斷線；關鍵點圓點就是原始列高亮的那一列；不引入圖表函式庫；卡片依照時間順序逐張出現 |
| **F5** | 結論與信心標籤 | 根因、引用了哪幾張證據卡、建議處置、信心標籤（High / Medium / Low，判定規則見開放問題 Q4） | 結論一定要引用至少 2 張證據卡；沒有引用證據的結論不能顯示 |
| **F6** | 證據不足灰卡 | 證據不夠時不硬下結論：灰卡標「Insufficient evidence」，列出已經查過的項目，建議人工巡檢 | 雙向驗收：正常資料一定出灰卡；真正的異常劇本不能被誤判成灰卡 |
| **F7** | 工單與 QR code | 結論確定後產生英文工單（產線、機台、根因、證據摘要、建議處置、時間），寫入 BigQuery 工單表；工單頁提供 QR code，手機可以直接開啟 | 用手機掃 QR 後 5 秒內在手機瀏覽器看到工單；不用登入；工單內容和結論卡一致 |
| **F8** | Demo 情境切換與重置 | 可以在「主線異常」和「正常資料」兩個情境之間切換，並把畫面重置到初始狀態 | 一鍵重置後可以馬上重演；資料集是固定的，但查詢和 Gemini 每次都真的即時執行 |
| **F9** | 響應式版面 | 四段寬度斷點（≥1600／1280–1599／1024–1279／<1024）加矮螢幕修飾；結論卡固定在面板頂端，證據卡收成精簡列（UI v2 §3） | 1920×1080、1366×768、1280×720 全螢幕整頁不捲動，結論卡（含 `Create work order`）不捲動就完整可見；結論出現後證據列 1080 高看得到 5 列、720 高至少 3 列（A1，2026-09-24 第二次會議標準）；<1024 改單欄堆疊，758px 寬時 Investigate 完整可點、沒有橫向捲軸 |
| **F10** | Before/After 收尾（Recap） | 工單視窗的 `Show summary`（或鍵盤 `S`）開啟收尾畫面：After＝這次調查由伺服器實測的秒數；Before＝人工調查基準（UI v2 §4） | After 和面板最後的 `Elapsed` 是同一個整數秒。Before 只有在 `MANUAL_BASELINE_MIN`（1–480 分鐘）和 `MANUAL_BASELINE_SOURCE`（出處說明）**兩個都設定且合法**時才顯示分鐘數、`Source: …` 和長條；只設其中一個或數值不合法，一律顯示 `—` 和 `Not yet measured for this plant.`，而且兩邊都不畫長條。app 裡不能寫死任何人工基準分鐘數（包括 40）；基準值只能來自訪談或實測（見 Q8）。不自動彈出；灰卡、失敗、調查中沒有 Recap |

## 6. 明確不做（MVP）

- 多產線、多工廠（只做 Line 2 一個異常劇本＋一個正常情境）
- 串接真實 PLC、MES 或感測器；只用模擬資料
- 預測性維護和任何預測功能
- 越南文、泰文介面（只在 pitch 的 roadmap 頁放一張越南文工單示意圖）
- 登入、帳號、權限管理
- 聊天輸入框和自然語言提問
- 讓 LLM 自己寫 SQL
- 推播通知（改用 QR code）
- Vertex AI Search／RAG、ADK、Agent Builder
- 3D；第 7 節「動態」以外的動畫（例如輸送帶動畫、停線燈號閃爍、數字跳動 count-up）
- 圖表函式庫、座標軸與格線、hover tooltip、可拖曳縮放的地圖；結論一出就自動彈出 Recap；「快 N 倍」這類倍數字樣

## 7. 非功能需求

| 類別 | 需求 |
|---|---|
| 延遲 | 從按下 Investigate 到出現結論，目標 ≤ 60 秒、上限 90 秒（對應分鏡格 ③–④）；第一張證據卡 ≤ 10 秒內出現；每個步驟都有逾時設定（建議 20 秒，由 Eddie 定）。 |
| 穩定性 | Cloud Run 開發期 min-instances=0，10/16–10/18 與評審期才改成 1 避免冷啟動（政策見 `docs/roadmap.md`）；min=0 時要實測冷啟動第一次請求的秒數。步驟逾時就退回該步驟的快取結果，並在畫面上標示「cached」，不能假裝是即時的；感測值缺值（NULL）要當成資料缺口處理，失敗的步驟不能一直停在執行中；回歸集 ≥ 9/10 才能部署。 |
| 成本上限 | GCP 現金上限等老闆拍板（Felix 提案）；預算警示設 50%、90%、100%，外加「預測達 100%」，第一天就設好。預算警示只會通知、不會自動停止，所以一定要搭配速率限制和快取。Gemini 逾時與 429 的重試次數要有上限；每次 Gemini 呼叫都要記錄 input／output／thinking token 與輪數，用來回填 `docs/finance/roi-model.csv`。碰到上限時的處理方式見 `docs/roadmap.md` 的停損點。 |
| 安全 | 公開網址要有速率限制（每 IP 的次數由 Eddie 定）；金鑰放 Secret Manager，不能寫進程式碼；服務帳號採最小權限（感測器資料唯讀，只能寫工單表）；本機用 `gcloud auth application-default login`（ADC），Cloud Run 用服務帳號身分，**不下載服務帳號 JSON 金鑰**，`.env` 只放專案 ID、區域等非機密設定；只接受 F8 定義的情境參數，不接受自由文字輸入；要測過 prompt injection（例如資料裡夾帶「忽略指示」）和缺值情境；不放任何真實客戶資料。 |
| 語言與視覺 | 介面和工單都是英文；深色底、琥珀色警示、Inter 字體（細節見 `docs/design/storyboard.md`、`docs/design/ui-v2-spec.md`）。 |
| 動態 | 只做 UI v2 §5 表列的有限動畫：調查時鏡頭拉近、證據卡進場與小圖畫線、根因高亮與閥門脈動（3 次後停）、灰卡拉回全景、Recap 長條。除了脈動以外，單一動畫不超過 800ms；會循環的只有調查中的焦點虛線框，結論一出現就停。`prefers-reduced-motion: reduce` 時全部關閉，直接顯示最終狀態。時間不夠時動畫可以砍（改成直接出現），高亮本身不能砍。 |

## 8. Demo 劇本主線

**主線：冷卻閥卡住 → 模具溫度上升 → 過溫停線**（模擬資料照這個故事造）

- 02:30 夜班交班（**干擾項**：時間接近，但不是原因）
- 02:41 Line 2 機台 3 的冷卻閥 CV-2 開度卡在 20%，冷卻水流量從正常值降到大約 40%
- 02:45–02:58 模具溫度持續上升，超過 SOP 4.2 節的警戒值
- 03:00 過溫警報觸發停線
- 期望的 Agent 結論：根因是「冷卻閥 CV-2 卡住」，信心 High；引用證據包括流量下降、溫度曲線、閥門開度紀錄，並排除交班這個因素；建議處置：依照 SOP 4.2 手動開閥、檢查閥門致動器
- 具體數值和欄位由 Eddie 依照這個故事產生，Dana 的分鏡數字也以這份資料為準

**加演：證據不足**

- 在正常資料情境（例如 Line 1 同一個時段、所有數值都在正常範圍）按 Investigate
- 期望結果：灰卡「Insufficient evidence」，列出已經查過的項目（溫度、流量、警報、交班紀錄），建議人工巡檢，不能硬掰一個根因
- Pitch 定位：這是信任賣點，要主動 demo，不是等評審來問

**回歸集**：10 題已知根因（含上面的主線，以及至少 3 題干擾項），由 Quinn 定義在 `docs/qa/test-plan.md`；灰卡的雙向案例也要放進去。
