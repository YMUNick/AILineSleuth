# 一人公司團隊會議

團隊成員是六個子代理，發言順序固定：
startup-pm → startup-engineer → startup-designer → startup-sales → startup-finance → startup-qa

## 1. 確認題目

從使用者的訊息取得「討論主題」和「輪數」。
- 沒說輪數就用 2 輪，最多 5 輪。
- 如果是討論目前的專案，先快速瀏覽專案結構和 README，寫一段 150 字內的「專案摘要」，之後每次都交給成員。
- 主題不清楚就先問使用者一個問題，不要猜。

## 2. 輪流發言

每一輪依序呼叫六位成員，一次一位（不要平行），因為每個人都要看到前面的人說了什麼。每次交給成員的任務內容要包含：

- 開頭寫「討論模式」
- 討論主題（以及專案摘要，如果有）
- 目前第幾輪、共幾輪；第一輪請他從專業角度提出觀點，中間幾輪請他回應其他人，最後一輪請他朝收斂與具體建議前進
- 到目前為止的完整發言紀錄，格式：【名字（角色）】發言內容

每位成員發言後，在對話中列出他的發言，讓老闆可以即時看到。

## 3. 整理結論

所有輪次結束後，你自己整理成會議結論，寫入 `docs/meetings/YYYY-MM-DD-主題簡稱.md`，內容包含：

- 一句話結論
- 共識
- 仍有分歧的地方（寫出各方立場）
- 各角色待辦（六個角色各 1~3 項，涉及檔案時寫出檔名）
- 錢的問題（預估成本、需要資金、回本時間；紀錄中沒有的數字標示為「待估算」，不要編造）
- 主要風險
- 建議老闆下一步（最多 3 點）
- 附錄：完整發言紀錄

在對話中顯示結論摘要和檔案路徑。

## 4. 詢問是否執行

最後問老闆要指派誰執行（可以多選，會依序進行）。在老闆明確回答前，不要修改任何檔案（會議紀錄除外）。

老闆指派後，一次呼叫一位成員，任務內容包含：
- 開頭寫「執行模式」
- 會議結論檔案的路徑（請他先讀）
- 老闆的額外交代（如果有）
- 前面成員已經改過哪些檔案

每位成員完成後，轉述他的回報，並建議老闆用 `git diff` 檢查改動。
